## 2) Brutal Truth Summary

### 2.1 Implemented and working in code

- User auth + OTP + onboarding flow exists (`apiserver/app/Http/Controllers/Api/Auth/*`, `OnboardingController`).
- MLM base entities exist: `stages`, `levels`, `user_subscriptions`, `affiliate_genealogy`, `affiliate_commissions`.
- Subscription activation upgrades user type from `regular` -> `member` (`SubscriptionService` line 111-125).
- Commission engine is modular (multiple calculators + processor service + events/jobs).
- Wallet/payment/order/recruitment handlers are routed from `HandlePaymentCompleted` listener.
- Frontend has user-type aware layout/navigation (`client/app/composables/useUserType.ts`).

### 2.2 Important truth that may surprise stakeholders

- `guest` is **not** a DB user type. It is a frontend state when `user` is null (`client/app/composables/useUserType.ts:55`).
- Auto promotion to `promoter/advisor/mentor` from subscription is **not** globally automatic in one central flow.
- `advisor/mentor` can be assigned from Filament job application actions (`JobApplicationsTable.php:191,212`).
- `promoter` creation happens in advisor team leader flow (`AdvisorTeamLeaderController.php:44`).
- Level promotion logic exists (`SubscriptionService::checkAndPromoteLevel`) but current references are mostly tests + explicit calls; no always-on scheduler/automation was found in this scan.

### 2.3 Code inconsistencies/gaps (real)

- `UserPermissionService` checks `$user->onboarding_completed_at` (`UserPermissionService.php:126`), but users table has `onboarded` boolean (`0001_01_01_000000_create_users_table.php:63`).
- `SubscriptionServiceInterface` method signatures differ from concrete `SubscriptionService` behavior (interface expects different return types for activation/promotion).
- Checkout route includes public exposure comment (`routes/api.php:393`) and is intentionally outside auth guard.

## 3) Domain Language (Simple Terms)

- User Type: lifecycle/business role (`regular`, `member`, `promoter`, `advisor`, `mentor`).
- User Status: account state (`draft`, `incomplete`, `active`, `subscribed`, etc.).
- Stage: subscription plan tier (price + benefits + matrix config + commission config).
- Level: progression steps inside a stage (qualification requirements and depth commission rates).
- Subscription: one user's purchased membership record tied to stage/levels.
- Genealogy: network tree stats and placement data for affiliate logic.
- Commission: payout ledger entries generated by events like subscription/order/task.

## 4) User Lifecycle (End-to-End, Actual)

## 4.1 Guest -> Registered User

Backend facts:
- Register endpoints create `users` row with referral parent mapping when referral code exists.
- Registration sets status to `active` in controller (`RegisterController.php:70,145`).
- Welcome notifications are dispatched (`RegisterController.php:77,152,187`).

Data facts on creation:
- `users.type` defaults to `regular` (`create_users_table.php:52-54`).
- `users.status` defaults to `draft` at schema level, but register controller sets active.
- `users.parent_id` stores sponsor/upline (`create_users_table.php:36-40`).

## 4.2 Login and Session

- Login supports password + OTP paths (`LoginController` auth module).
- Frontend treats unauthenticated state as `guest` layout (`useUserType.ts:55`).

## 4.3 Onboarding Completion

`OnboardingController` flow:
- contact verification via OTP (`verifyContact` at line 57+)
- sets `email_verified_at` or `mobile_verified_at` (`line 118,123`)
- marks onboarding complete with `onboarded = true` (`line 149`)

`User::isOnboardingComplete()` also checks:
- `onboarded` true
- at least one address exists
- email or mobile verified (`User.php:278-283`)

## 4.4 Regular -> Member Transition (Subscription)

This is a real automatic transition:
- subscription activation calls `SubscriptionService::activateSubscription()`
- inside it, if user is regular, update to member and set `subscribed_at` (`SubscriptionService.php:111-116`)

Activation side effects in same flow:
- lock + idempotency check (`line 86-102`)
- mark subscription active/paid
- ensure genealogy exists
- increment upline counters
- propagate sales/PV
- process and persist commissions
- dispatch `SubscriptionActivated` event

## 4.5 Member -> Promoter/Advisor/Mentor (Current Truth)

There is no single unified central "career ladder" service auto-updating all types by level.

Observed flows:
- Promoter creation path in advisor team leader controller (`AdvisorTeamLeaderController.php:37-48`).
- Advisor assignment via Filament job app action (`JobApplicationsTable.php:191`).
- Mentor assignment via Filament job app action (`JobApplicationsTable.php:212`).

Meaning:
- type evolution above member is partly operational/admin driven, partly feature-flow driven.
- it is not purely computed from `stage+level` at one central place.

## 5) MLM Engine: How It Works Today

## 5.1 Core Tables and Purpose

- `stages`: plan economics + matrix dimensions + commission config.
- `levels`: requirements and commission rates per depth.
- `user_subscriptions`: user's paid lifecycle and current/highest level.
- `affiliate_genealogy`: counters, sales/PV and placement metadata.
- `affiliate_commissions`: full commission ledger (gross/net/tds/tcs/admin fee/status).

## 6) Earnings Map (Where User Can Earn Right Now)

Actual earning channels in codebase:
- Sponsor/level/originator/task commissions (based on enabled calculators + triggers).
- Wallet credits/debits + transaction records.
- Order completion may trigger affiliate commission processing via payment completion listener.

Subscription-driven earnings path:
1. User buys plan.
2. Subscription activates.
3. Commission processor computes and writes affiliate commission rows.
4. Downstream payout/ledger visibility handled in commission/wallet modules.

Order-driven path:
1. Payment completed event routes to `handleOrderConfirmation()`.
2. `OrderValidationService` invoked with `CommissionProcessorService`.

Trace:
- payment router: `HandlePaymentCompleted.php:70-91`
- order path: `277-308`

Note:
- Not every documented business concept from old plans is guaranteed to be fully wired in runtime. Current truth is event handlers + calculators currently registered.

## 11) Known Gaps and Absurdities (Direct)

- Interface drift:
  - `SubscriptionServiceInterface` expects
    - `activateSubscription(...): UserSubscription`
    - `checkAndPromoteLevel(...): array`
  - Concrete `SubscriptionService` currently returns array for activation flow and `?Level` for promotion.
- Permission onboarding field mismatch (`onboarding_completed_at` vs `onboarded`).
- Career/type evolution is spread across admin/table actions and team leader flow; no single policy service guaranteeing consistent business progression.
- Level promotion capability exists but not found as a guaranteed automatic runtime job in this pass.

## 12) Business Perspective: What Is Ready vs What Needs Hardening

Ready enough (current implemented core):
- user onboarding, subscription purchase, member transition, genealogy maintenance, commission calculation pipeline, wallet/order/recruitment payment routing.

Needs hardening for enterprise confidence:
- unify type progression policy in one service
- resolve interface drift and permission field mismatch
- document and enforce auto-promotion trigger strategy (cron/event/command)
- increase invariants around public checkout path security review
